# QingTransfer 跨设备传输与远控规划（讨论稿）

PC 与 Android 的分层消息、配对互通及授权规则草案见 [设备通信协议 DCP/1](DEVICE_COMMUNICATION_PROTOCOL.md)。

状态：**核心产品方向已确认；Windows 和 Android 开发版已有发现、双端确认配对及已配对设备操作的代码。Android 已把设备列表与原有文件传输入口放在同一“设备”页，但旧传输仍使用独立协议；跨平台双端确认、离线撤销同步、亲密设备电量发送、统一加密传输、四向文件收发及远控尚未完成真实设备验收。本文不是发布说明。**

## 1. 目标与术语

将 QingTransfer 从 Windows 局域网文件互传，扩展为 Windows 与 Android 工具箱都能直接使用的跨设备入口：设备列表、文件传输、远程查看/控制、可选择共享的设备状态。本文将需求中的“PE”按**手机端 Android**理解；iOS、互联网中继和云账号暂不进入首期。

“PC → 手机”表示 **PC 发起、手机作为被操作/接收端**；反方向同理。文件发送方向与远控发起方向要分别标明，避免“控制端”和“文件接收端”混淆。

| 路径 | 文件互传 | 远控目标 | 首期应验证的输入 |
| --- | --- | --- | --- |
| PC → PC | 双端收发 | PC 控制 PC | 鼠标、键盘、多显示器 |
| 手机 → PC | 双端收发 | 手机控制 PC | 触摸转指针/滚动/键盘、横竖屏 |
| PC → 手机 | 双端收发 | PC 控制手机 | 鼠标转触摸、返回/Home 等受支持动作 |
| 手机 → 手机 | 双端收发 | 手机控制手机 | 点按、滑动、多指能力评估、横竖屏 |

四条路径是最终交付目标，不承诺四条路径会在同一里程碑同时上线；每条都要在真实设备上验收。被控端必须能显式拒绝、结束会话。

## 2. 仓库现状与集成边界

- Windows 当前的 `QingToolbox.Tauri/native-transfer` 是独立 Rust 进程模块，已有 mDNS 发现、nonce 回显探测、双方确认和文件流传输。它的探测只证明端口响应，不证明设备身份；现有 TCP 握手不能直接作为远控、亲密关系或敏感数据共享的认证基础。
- 现有 Android 规划见 [`../plans/013-android-mobile-shell-and-root-capability-foundation.md`](../plans/013-android-mobile-shell-and-root-capability-foundation.md)：它将四向文件传输列为后续目标。本文是新的产品方向草案，不表示 Android 已有可用的传输/远控实现。
- **已确认的“内置”产品形态**：Windows 与 Android 安装包均自带设备互联功能，主界面只有统一“设备”入口，用户不必另装 `.qmod`。设备身份、关系、文件传输、远控和共享状态属于同一个设备产品能力；不再把文件传输设计为与“设备”平行的长期独立入口。这被视为原有“本体不内置具体工具功能”原则的一项明确产品特例；实现上仍把发现/配对、传输和音视频/控制引擎隔离在受监督的原生组件中，避免把编解码和网络会话全部塞进 Shell。
- 设备互联总开关及后台发现要有清晰的首次启用步骤；未启用时不启动远控监听和敏感信息采集。Windows/Android 可有不同的平台适配层，共享的是协议和产品语义，不强求同一套 UI。

### 统一“设备”入口的迁移边界

- 一个设备条目承载身份与关系；在**已验证公钥的新加密会话**上分别发起传文件、远控和状态共享。在线、已配对、亲密关系、正在传输是独立状态，不因点开文件传输而自动互相信任。文件传输入口最终放在连接后的**设备操作按钮**内，不单列为设备首页的常驻主按钮；当前 Android 旧传输入口只是迁移期兼容。
- 四向文件互传（PC↔PC、PC↔Android、Android↔Android）共用 `file.v1` 授权和传输状态机，两端都可发送或接收；发送文件、接收目录、进度、取消和失败记录都从“设备”页进入。UI 可以按平台布局不同，但不能让用户为同一台设备维护两套互不相认的身份列表。
- 迁移期间保留旧 QingTransfer 入口与能力，避免现有文件互传回退；**旧传输会话不具备新设备配对身份**，不能借此访问亲密关系、通知或远控。Android 当前只是将旧入口收纳到“设备”页；不能把这一界面合并称作底层协议已合并。
- 等 `QDS1` 已配对会话和 `file.v1` 在四条路径完成真实设备验收后，切换“设备”页的发送/接收操作到新引擎，迁移接收设置，再退役重复的旧传输入口和旧发现协议。不要在新引擎未完成前直接删除旧模块或把旧明文流量自动升级为可信设备流量。

## 3. 三种设备关系不是在线状态

关系保存在**本机对某个已验证设备公钥**的记录上，不以设备名、IP、mDNS 广播或“当前连着”判定；在线/离线、正在传文件、正在远控是另外的状态。

| 关系 | 判定/进入方式 | 默认可见内容 | 电量共享 | 通知共享 | 传输与远控 |
| --- | --- | --- | --- | --- | --- |
| 陌生设备 | 仅被发现，未完成验证配对 | 最少的公开昵称、平台、可配对状态 | 不共享 | 不共享 | 只能请求配对；配对前不能传文件或远控 |
| 连接设备 | 陌生设备完成双向验证配对后**默认进入** | 已授权的基本设备信息、在线状态 | **默认关**，设备主人可开 | **默认关**，设备主人可开 | 可发起请求；每次远控由被控端批准 |
| 亲密设备 | 本机发起、**双方分别同意**后从“连接设备”升级 | 同上 | **默认开** | 实现后应用内**默认开**，仍须系统权限；当前尚未实现 | 可简化设备列表操作，但远控屏幕与控制权限仍独立授权 |

“亲密”是双方用户主动确认的关系，不是 LAN 自动判断的“同一人”。配对成功只能进入“连接设备”；升为“亲密设备”需要已认证连接及两端分别同意，双方收到结果提示；在线断开也需要两端同意。对方离线时仍允许本机立即撤销信任，并持久保存待同步记录，重遇对方且验证其公钥后同步撤销并提示。没有账号时只能验证**设备密钥**和人工确认，不能技术上证明两台设备归同一人。密钥变化、重装应用后必须重新验证。

共享设置由**数据所属设备**逐台决定，可随时撤回；一端把对方标为亲密，不得自动打开对方的分享。这里“默认开”指配对且本机功能与系统权限都已启用之后的应用内默认值，**不代表跳过 Android 系统授权**。陌生设备即使猜到设备 ID 也读不到状态。

建议拆成可独立关闭的两类数据：

1. **设备状态**：手机向亲密设备（Windows 或另一台 Android）约每分钟发送一次电量百分比/充电状态，只在已验证公钥、对端可达且设备互联服务运行时发送；读数过期就不再显示为当前值。Windows 电量视硬件支持后续补充。[Android BatteryManager](https://developer.android.com/reference/android/os/BatteryManager)。
2. **通知**：Android 的应用通知/短信通知可作为同一通知来源的摘要展示；需用户在系统设置单独授予通知访问，再由用户按设备及可选的应用白名单控制共享。亲密设备默认以**摘要**为主；当通知中有系统允许读取的验证码时，**验证码卡片优先于普通通知显示，代码本身清晰可见**，但只对该已授权的亲密设备短暂展示，不写常规日志或长期历史。锁屏受保护内容、系统隐去的字段和未授权应用消息不读取；不承诺读取短信数据库或所有应用消息。通知访问不可用时显示原因，不退化为偷偷读取其他来源。[Android NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService)。

**验证码优先是展示规则，不是获取能力保证。** Android 15 对普通通知监听器可能隐去 OTP；更高版本还存在受限敏感通知权限。技术验证阶段评估系统认可的 CompanionDeviceManager 关联是否适用于 QingToolbox 的设备形态和分发方式，不以规避系统隐去为方案。若验证码已被系统隐去，界面仅提示“验证码受系统保护，无法在此设备显示”，不伪造或旁路读取。[Android 15 OTP 行为变更](https://developer.android.com/about/versions/15/behavior-changes-all)、[敏感通知权限](https://developer.android.com/reference/android/Manifest.permission)、[CompanionDeviceManager](https://developer.android.com/develop/connectivity/bluetooth/companion-device-pairing)。

关系降级、断开或退出登录（若未来加入账号）后立即停止推送并清除远端缓存。连接设备即使后来开启普通通知共享，是否同时允许验证码应由独立开关决定；建议默认仍关闭，避免把朋友设备当作自己的亲密设备。

## 4. 文件传输与远控是两种独立授权

- 文件传输继承现有进度、取消、接收路径和哈希校验思路，扩展到四向的多文件/文件夹；目录项要验证相对路径，不让远端指定任意写入位置。传输权限不得等同于远控权限。
- 远控分为**观看屏幕**和**发送输入**两级。每次会话在被控端展示对方身份、请求能力和明显的“结束”入口；朋友设备默认每次确认。亲密设备可讨论“记住观看授权”，但首期不提供 Android 无人值守控制，也不绕过系统录屏授权。
- 任何设备都应能一键停止屏幕采集、输入和文件会话；网络断开/锁屏/系统撤权时清理会话密钥与输入状态，禁止残留按键或继续展示上一帧的敏感内容。

### 平台实现可行性边界

- Windows 被控端：候选方案是 Desktop Duplication 获取屏幕帧、受限输入接口注入操作；需处理多显示器、旋转、DPI 和保护内容。普通进程的输入注入受 Windows 完整性级别限制，**不承诺操作 UAC 安全桌面或高权限窗口**。[Microsoft Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)、[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)。
- Android 被控端：屏幕输出考虑 MediaProjection，用户须批准采集且需要符合前台服务要求；较新 Android 版本对每次采集会话重新授权。输入候选为用户主动启用、明确声明手势能力的 AccessibilityService；它不是 Root，也不能保证所有系统/受保护界面都可控。必须先做真机技术与分发政策验证，再承诺 PC → 手机和手机 → 手机“完整远控”。[MediaProjection](https://developer.android.com/media/grow/media-projection)、[AccessibilityService](https://developer.android.com/reference/kotlin/android/accessibilityservice/AccessibilityService)。
- Android 的原生权限、采集和手势能力可以通过 Tauri 2 的 Kotlin 移动插件接到 Rust 状态机，不要求 Vue 直接获得系统权限。[Tauri 移动插件](https://v2.tauri.app/develop/plugins/develop-mobile/)。

## 5. 手机控制端：全屏与小窗

全屏是完整交互模式：远端画面按**等比适配**显示，留黑边而不拉伸；输入只在实际画面区域生效，并通过归一化坐标映射到远端原始分辨率。旋转、折叠屏、刘海/安全区、软键盘和远端分辨率变化都要重算映射；PC 多屏先提供选择屏幕，不把多个分辨率强行合并为一个触摸面。根据网络与设备能力协商帧率、码率和编码分辨率，不默认修改被控设备的系统分辨率。

**已确认的小窗形态**：首期使用系统画中画（PiP），缩成可移动的远端画面预览，点按返回全屏继续控制；小窗本身不承担完整远端触控，只保留极少的结束/静音等动作。Android 官方说明 PiP 内不能直接操作应用的普通 UI 控件。[Android PiP 指南](https://developer.android.com/develop/ui/views/picture-in-picture)。交互式悬浮层不列入首期。

## 6. 协议与安全底线

1. 发现沿用 LAN 广播思路，补 QR/手动地址回退；发现结果只用于“候选设备”，不可授予信任。
2. 每次安装生成本地设备密钥；配对时两端核对短验证码/二维码并绑定公钥。会话使用相互认证、加密传输、重放防护和短生命周期会话密钥；不能只靠明文 TCP、mDNS 名称或当前的 probe nonce。
3. 协议明确区分 `discover / pair / status / file / screen / input` 能力和版本。跨设备协议版本独立于当前工具箱的模块 `apiVersion: 1`，升级时不把两种版本混为一谈。
4. 控制指令采用后端固定 allowlist 和当前会话授权，不接受 Vue 提交任意系统命令、文件路径或输入设备句柄。视频帧与通知正文不写常规日志；断线不自动恢复高权限会话。
5. 被控端持续显示可见的共享/控制提示与停止入口；陌生设备不允许无提示后台远控。局域网也按不可信网络处理。

Windows 与 Android 开发实现使用独立 `_qingdevice._tcp.local.` 发现、Noise XX 握手和双方显示的 8 位校验码。两端各自确认后才持久化对端静态公钥；本机私钥分别由 Windows DPAPI、Android Keystore 封装密钥保护。发现 ID、设备名、IP、响应端口都不是信任凭据。用户关闭发现、拒绝或超时不会建立关系。配对记录仅代表已验证的关系，尚不代表当前在线，也不授予传输、远控或通知读取能力。跨平台的双方确认及密钥持久化仍需真机共同验收；不得把 Windows 私钥文件直接复制到手机。

## 7. 建议交付顺序与验收

| 阶段 | 产物 | 退出条件 |
| --- | --- | --- |
| A. 规格与真机验证 | 威胁模型、设备身份/权限协议草案；Windows 与 Android 的录屏、编码、输入、PiP 技术样机 | Android 目标系统版本和分发方式上的权限行为实测；明确哪些受保护画面/输入不可做 |
| B. 可信设备与传输 | 双端配对/撤销、三种关系、四向单/多文件与文件夹传输；旧 Windows v1 传输安全迁移 | 四向传输完成哈希校验、取消/断线清理；未配对者无法获取私有状态 |
| C. 远控 PC | PC → PC、手机 → PC 的屏幕流、输入和会话确认 | 真实高低分辨率、多屏、横竖屏与弱网测试；UAC 限制明确提示 |
| D. 远控 Android 与小窗 | PC → 手机、手机 → 手机；手机全屏与 PiP 小窗 | Android 系统录屏/手势授权、旋转、PiP 返回全屏、主动/系统撤权结束均通过真机验收 |
| E. 状态共享 | 电量、通知摘要、验证码优先卡片、逐设备开关和撤销 | 亲密默认开/连接默认关/陌生不可见；有权限且可读取时优先显示验证码，系统隐去时明确提示；关系降级后停止推送 |

各阶段保持已有文件互传可用；不能把 v1 明文连接或未验证设备“自动升级”为远控可信设备。发布前需要两台 PC、两台 Android 的交叉组合及不同 Android 版本实测，不能只用模拟器证明四向可用。

## 8. 已确认的产品决定与待验证问题

1. **内置形式已确认**：双端安装包自带、主界面直接可用，无须另装模块；内部引擎保持隔离是建议的技术实现。
2. **手机小窗已确认**：画中画预览，点按返回全屏控制；首期不做小窗内直接远控。
3. **亲密通知已确认**：应用内默认开启通知共享，以摘要为主；系统实际提供验证码时优先、清晰展示。Android 系统通知权限仍须用户手动授予。

待验证：Android 各版本上验证码可见性、受信任伴侣设备关联是否适用、Android 被控输入能力和分发政策。验证不通过时按系统能力降级，并把限制明确呈现给用户，不承诺绕过。单机两个隔离身份可验证 Windows 发现、加密握手、双方确认与关系切换；真实跨设备网络、系统权限与远控仍须双端真机验收。
